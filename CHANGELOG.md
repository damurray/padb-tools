- **Watcher retention: `--keep-inputs N`, `--keep-results N`, `--prune-now`.** The watcher snapshots every input into `<out>/_inputs` because PadbLoader prunes old runs (a snapshot is then the ONLY copy) -- and nothing trimmed those snapshots, so they grew by one file per run. Now: `--keep-inputs N` (default **14**, PadbLoader's own window) keeps the snapshots of the newest N runs per stream, `--keep-results N` (default **0 = keep every result**, deliberately conservative: results are what people read) the result folders; 0 keeps all. **"Newest" is by the run stamp in the file name**, not by processing order, so a late-arriving older run is the one pruned. Only FINISHED (`done`) runs are pruned (a run that was given up on keeps its snapshot so `--retry-failed` still works); the ledger entry stays, marked `inputs_pruned` / `results_pruned`, so a pruned run is **not analysed again** while its source file exists and the overview says "(results pruned)". **A delete is only ever done on a folder at exactly the expected place** (`<out>/_inputs/<stream>/<folder>` or `<out>/<stream>/<folder>`), strictly inside the output folder, never in `_inputs` for a result, and with no symlink / junction on the way: a damaged or tampered ledger cannot make it delete anything else (refusals are logged and counted). Removing a hard-linked snapshot never touches the original. Applied after each pass; `--prune-now [--dry-run]` applies it once and exits (refused while another watcher holds the folder). **Verified (`qa_watch`, 75 checks now):** keep counts, per-stream independence, only finished runs, newest-by-stamp, no re-analysis after pruning, the original is untouched, dry run changes nothing, `--prune-now` and its lock, a tampered ledger (outside the folder, at `_inputs`, at the output folder) and junctions (to outside, and -- the case only the link check catches -- to another snapshot inside) all refused. 8 mutations each caught (one scenario was missing and was added).
- **v3.0 stage 7 (directory watcher) -- `padb_watch.py`: watch a folder for new parquet files and analyse each one, once.** `py padb_watch.py --padbloader --out D:\padb\watch` follows PadbLoader's scheduled output (loops); `--watch DIR` watches any folder; `--once` is one pass for Task Scheduler; `--discover` prints where PadbLoader writes and why. **Built from PadbLoader's own source** (read 2026-11-24), because its behaviour dictates the design: the export folder is the user's choice (`user-settings.json` `ExportDirectory`) > `Export:OutputDirectory` > `<root>\Exports` (root = `%LOCALAPPDATA%\PadbLoader` or `PADBLOADER_DATA_DIR`); parquet goes to `<export>\PadbLoader Data\` (manual) and `...\Scheduled\<schedule> - <owner>\<name>_<yyyyMMdd-HHmmss>.parquet` (scheduled, one new file per run) -- `--padbloader` watches the Scheduled folder (on this PC `C:\Users\damurray\AppData\Local\PadbLoader\Exports\PadbLoader Data\Scheduled`). **Hazards handled, each by a test:** the final parquet is written IN PLACE at its real name (no temp-then-rename), so a file is COMPLETE only when it has not been modified for `--settle` seconds, its size and mtime do not change on a re-stat, it ends with the `PAR1` magic AND its footer parses; `.staging-*` / `<file>.parquet.parts` folders (they contain `*.parquet`!), `.partial`, dot files, `.dbdif` / `.csv` and deeper folders are ignored; an empty / failed / cancelled run DELETES its file and **PadbLoader prunes runs beyond `KeepLastRuns` (default 14)**, so every input is SNAPSHOT (hard link on one volume, else a copy) into `<out>/_inputs` before it is analysed and a vanished file is recorded, not an error. Output: `<out>/<stream>/<file>/` (what `padb_analyze` writes), `<out>/index.html` (every run, newest first), `watch_log.txt`, `watch_status.json`. **Verified (`qa/qa_watch.py`, 59):** discovery vs PadbLoader's resolution order (and this PC), the scan rules, completeness (truncated, header-only, empty, magic-but-no-footer, fresh, still growing), the ledger rules, restart / re-write / give-up / crash / vanish / wait-then-complete passes, snapshot survives deleting the original, escaping in the overview, the lock, the real subprocess runner (junk output, failed analysis, hung analysis killed with its child), and the real CLI end to end through `padb_analyze` for a padb-tools parquet AND a genuine padbloader-schema parquet. 14 mutations, see QA_GUIDE. **Not done, stated plainly:** no Windows-service wrapper (run it from Task Scheduler with `--once`, or leave `--padbloader` running); it does not talk to PadbLoader (it only reads the folder); padbloader runs need an open signed-in page, which is PadbLoader's constraint, not ours.
- **SECURITY (web app): a loopback guard -- requests that do not come from the app's own page on this machine are refused.** The app has no login and ~20 state-changing POST routes (run / delete / schedule a job, open Explorer or the viewer, kill processes, change the default share). Binding to `127.0.0.1` does not keep a web page in the user's own browser out, and BOTH classes were **reproduced in a real browser before the fix** (`qa/qa_websecurity.py` against the unguarded app: 14 checks failed): (1) **CSRF** -- a page on another origin (`attacker.localhost`) posted to the app by `fetch(mode:'no-cors', text/plain)` and by a `<form enctype=text/plain>`; both are "simple requests" (no preflight) and the routes read the body with `get_json(force=True)`, so the action ran (the attacker cannot read the reply); (2) **DNS rebinding** -- a request whose `Host` is a hostile name was answered (the job list was returned, a POST took effect), which in a rebinding attack is same-origin to the browser so the attacker CAN read everything. **The guard** (`webapp/padb_web.py`, a `before_request`): the `Host` header must be a loopback name (`127.0.0.1`, `localhost`, `[::1]`, any port; userinfo tricks refused); a state-changing request must carry an `Origin` equal to its own origin (so `null`, another site, another local app on another port and `https` are all refused) or, with no `Origin`, a `Sec-Fetch-Site` of `same-origin` / `none`; clients that send neither (curl, the Flask test client, scripts) are not browsers and are unaffected; a refusal is a clear JSON 403 and is logged. Reads (`GET`) are served to a loopback `Host` regardless of `Origin` (without CORS a browser cannot read a cross-origin reply). **Verified (`qa_websecurity`, 27):** the same real-browser attack now changes nothing; the app's own page still works in a real browser via both `127.0.0.1` and `localhost` (own-page POST and GET); a hostile-`Host` socket request is refused (GET and POST); a 17-case Host / Origin / Sec-Fetch-Site matrix over a real socket, each case also asserting the refused request's EFFECT never happened; the existing test client is unaffected. Teeth by mutation (7, see QA_GUIDE). **Not changed:** the server is still the Flask dev server (threaded, `127.0.0.1` only) -- a production server would not have fixed this; there is still no login (a local process running as the same user can still call the API, which is outside this threat model).

### Build speed (output byte-identical)

Coverage depends only on `n` and the gap `k = j - i`, so it is now one cached vectorised table per `(n, P, C)`; the narrowest-window tie-break is preserved exactly (n=300: 2.03 s -> 0.0002 s).
